# 网格与图块方案

32×32 之所以显得"不够用"，不是数字本身小，而是**三件本该独立的事被绑成了一个常量**。

---

## 一、问题的本质

现在的 `ArpgData.TILE := 32` 同时承担了三种角色：

| 它是什么 | 谁在用 |
|---|---|
| **逻辑网格**：寻路、房间、走廊、仇恨范围、小地图的坐标单元 | `dungeon_gen` / `party_manager` / `ai_controller` / `minimap` |
| **美术图块**：图块集切分与渲染单元 | `world.gd` 的 `SRC_FLOOR = Rect2(32,32,32,32)` |
| **实体尺度**：角色的直观大小 | 玩家 16px、Boss 直径 27px |

只要它们共用一个数字，改任何一个都会牵动另外两个：换 64 的图块就要重画地牢，放大角色就要重调平衡。

**方案的核心是把这三者拆开。**

---

## 二、三层坐标系

```
世界坐标 (px)          ← 渲染、碰撞、特效、镜头，一切"看得见"的东西
    ↑ ÷ grid_size
逻辑网格 (grid)         ← 寻路、房间、走廊、小地图，一切"算得出"的东西
    ↑ 仅渲染时换算
美术图块 (tile)         ← 图块集切分与绘制，只影响观感
```

三条规则：

1. **逻辑网格是唯一的真值坐标系**。关卡数据、AI 判断、存档一律存格子坐标，不存像素。
2. **美术图块只是渲染单元**，可以比格子大（一个图块画在 2×2 格上），也可以比格子小（一格放 4 个小图块）。
3. **实体用半径描述，不"占格"**。所谓 footprint（占几格）是由半径**算出来**的派生量，用于寻路时膨胀障碍，不是需要手填的属性。

---

## 三、网格尺寸怎么选

网格是**性能与精度的总开关**：它同时决定 A\* 的节点数、空间哈希的桶数、房间能画多细。

| 网格 | 适合 | A\* 节点量（以 44×32 地图计） | 代价 |
|---|---|---|---|
| 64 | 角色 ≥48px、粗略关卡 | 1408 | 走廊至少 128px 宽，地图利用率低 |
| **32（默认）** | 角色 ≤32px，当前全部敌人 | 1408 | 平衡点 |
| 16 | 小角色、精细关卡 | **5632（×4）** | 万敌压测下寻路成本显著上升 |

**结论：网格保持 32，不跟着图块或角色改。**

理由是硬性的：这个项目的地牢是程序生成 + 万敌压测，网格缩一半 = A\* 节点 ×4 = 压测帧率腰斩；而**放大角色根本不需要改网格**——让角色占 2×2 格就行。反过来说，如果真需要 64 的宏观网格，正确做法是新建一层"区块"概念（若干格子合并成一个房间单元），而不是把 A\* 的粒度调粗。

网格尺寸做成可配（`ArpgData.GRID`），但**默认值与现有平衡一致**，改它属于"换一个玩法"级别的决策，不是日常调参。

---

## 四、图块尺寸怎么选

图块尺寸**完全自由**，因为它只影响渲染：

| 关系 | 效果 | 典型用途 |
|---|---|---|
| `tile = grid` | 1 图块 = 1 格，最直观 | 默认 |
| `tile = 2×grid` | 一个图块覆盖 2×2 格，画面更"厚" | 大砖块、巨型地砖 |
| `tile = grid/2` | 一格放 4 个图块，细节翻倍 | 装饰、地面纹理 |

**渲染时按世界坐标画**：图块位置 = `格子坐标 × grid`，图块大小 = `tile`。两者互不约束。

场景编辑器里一个"格"始终等于一个**图块**（这样画起来最直观），导出时额外记录 `grid_size`，
游戏侧据此建立寻路网格并换算渲染位置。

### 图块集尺寸的自动识别

导入 PNG 时按"能被常见图块尺寸整除、且列数在合理区间"来推荐：

```
候选尺寸 16 / 24 / 32 / 48 / 64
评分：能整除得基础分，列数落在 8~32 之间加分，行数同理
取最高分；相等时偏向 32
```

这样用户丢一张 512×384 的图进来，推荐 32（16×12 格）；丢 768×576 的进来，推荐 48（16×12 格）。
**推荐值可以被手动改**，改完立刻按新尺寸重切调色板。

## 五、角色较大时怎么处理

这是方案的关键部分。四条规则一起用，缺一不可。

### 5.1 脚底锚点（解决对齐）

所有实体的 sprite 原点统一定在**脚底中心**，不是图片中心。

```
     ┌─────┐
     │ 角色 │   ← 图片
     └──┬──┘
        ●        ← origin（脚底中心）= 世界坐标 position
   ─────┴─────   ← 地面
```

好处：16px 的小怪和 96px 的 Boss 站在同一格时，**脚在一条线上**，不会出现"大角色陷进地板/浮在空中"。
代价：所有美术资源要按这个约定切图；程序化绘制的角色（本项目现状）在绘制时把 y 偏移减掉自身高度即可。

### 5.2 半径独立于网格（解决尺寸）

`radius = base_radius × scale`，与网格无关。当前 `base_radius = 9`：

| 实体 | scale | 半径 | 直径 | 占几格（grid=32） |
|---|---|---|---|---|
| 小恶魔 | 0.9 | 8.1 | 16 | 1×1 |
| 剑士/狼 | 1.0 | 9.0 | 18 | 1×1 |
| 骑士 | 1.1 | 9.9 | 20 | 1×1 |
| **Boss** | **1.5** | **13.5** | **27** | **1×1** |

**现在全都在 1 格内**——所以"角色变大"这件事目前根本没发生过，方案是为将来准备的。

分界点很明确（`footprint = ceil(直径 / 32)`）：

| 直径 | footprint |
|---|---|
| ≤ 32 | 1×1 |
| 32 ~ 64 | 2×2（`scale ≥ 1.78` 起） |
| 64 ~ 96 | 3×3（`scale ≥ 3.56` 起） |

所以要让 Boss 占 2×2 格，把 `scale` 从 1.5 调到 **1.8** 即可；
占 3×3 调到 3.6。**不需要改任何网格代码**，走廊宽度也会自动跟着变宽（见 5.4）。

### 5.3 footprint 是算出来的（解决寻路的"能不能过"）

```
footprint = max(1, ceil(diameter / grid))
```

直径 27 → 1 格；直径 65 → 3 格；直径 96 → 3 格。

寻路时据此**膨胀障碍**（clearance map）：一个格子对 3×3 的实体可走，当且仅当以它为中心的
3×3 邻域全是地板。这样大角色不会"卡在门口进不去还一直撞"。

实现上不必每帧算：换层时算一次 `byte[] clearance`，A\* 查询时按实体的 footprint 查对应位。
千级格子的地图，这个数组只有几十 KB。

### 5.4 走廊宽度必须 ≥ 最大实体（解决"生成出进不去的图"）

生成器打洞时是 2×2 格宽（64px）。如果某一层会出现直径 96 的 Boss，走廊就必须 ≥ 3 格。
**在生成阶段读当前层最大实体的 footprint，作为走廊宽度的下限**，而不是事后靠玩家撞墙发现。

这是唯一需要"生成器知道玩法参数"的地方，属于合理耦合。

## 六、限制（必须提前知道）

| 限制 | 原因 | 缓解 |
|---|---|---|
| **网格不能随便调小** | A\* 节点数随 1/grid² 增长，万敌压测顶不住 | 网格固定 32，尺寸需求靠 footprint 消化 |
| **直径 > 走廊宽 = 卡死** | 圆形碰撞体过不去 | 生成时校验走廊下限（5.4）；或给这类实体单独开宽阔房间 |
| **大角色寻路更慢** | 膨胀后 A\* 有效节点变稀，长距离路径要绕 | 只要不是全场都是 Boss 就无感；必要时给大角色做专用导航层 |
| **窄走廊里圆形会卡** | 碰撞滑动在拐角处可能顶住 | 保持走廊 ≥ 直径 + 留 1 格余量 |
| **空间哈希查询范围随半径增长** | 每帧邻近查询要扫更多桶 | 半径 ×2 = 桶数 ×4，千级实体仍在预算内 |
| **脚底锚点要求美术统一** | 混用"中心锚点"和"脚底锚点"会错位 | 在资源规范里写死；程序化绘制统一用 `pos - Vector2(0, h/2)` |

**一句话总结**：网格定死、图块自由、尺寸靠半径、对齐靠脚底、通行靠膨胀。
这四件事各自独立之后，"换图块"和"放大角色"都变成改配置而不是改架构。
